## Фаза 1 — Починка релевантности поиска (reranking)

**Зачем:** `qdrant_search` сейчас возвращает top-5 чанков просто по косинусному сходству, без порога — если в базе один большой документ, на любой вопрос вернутся 5 кусков именно из него, даже нерелевантных.

**Что делаем:** добавляем reranking через Voyage (тот же провайдер, что уже используется для эмбеддингов) — берём из Qdrant пул побольше (~20 кандидатов), прогоняем через rerank-модель, оставляем реально топ-5 по смыслу.

- [ ] `RerankProtocol` + `VoyageRerankProvider` (`app/providers/rerank/`)
- [ ] `RerankService` (`app/services/rerank.py`)
- [ ] `get_rerank_provider()` в `app/core/providers.py`
- [ ] Конфиг: `RERANK_ENABLED`, `RERANK_CANDIDATE_POOL`, `RERANK_MIN_SCORE`
- [ ] `SearchService.search()` — двухэтапный поиск (кандидаты → rerank → top-k)
- [ ] Прокинуть `RerankService` в конструктор `SearchService` (`app/main.py` lifespan)
- [ ] Мелкая уборка: удалить мёртвый `complete_with_tools` (protocol.py/groq.py/llm.py)

**Проверка:** спросить про тему, которая релевантна только части документов — убедиться что в `sources` больше нет случайных чанков не по теме.

## Фаза 2 — Graph RAG

**Зачем:** связывать факты из разных чанков/документов через граф сущностей (например "кто отвечает за то, от чего зависит Atlas").

**Решение:** без нового LLM-тула (чтобы не трогать хрупкий tool-calling) — граф-контекст подтягивается автоматически, обычным SQL-запросом, поверх уже отработавшего `qdrant_search`.

- [ ] 3 новые таблицы: `entities`, `relationships`, `entity_mentions` + миграция
- [ ] Конфиг: `GRAPH_EXTRACTION_ENABLED`, `GRAPH_EXTRACTION_BATCH_SIZE`, `GRAPH_EXTRACTION_MAX_CHUNKS`, `GRAPH_CONTEXT_MAX_ENTITIES`, `GRAPH_CONTEXT_MAX_RELATIONSHIPS`
- [ ] `GroqLLM.complete_json()` — JSON-режим (не tool-calling) для извлечения сущностей
- [ ] `app/schemas/graph.py` — валидация ответа LLM
- [ ] `EntityRepository` / `RelationshipRepository` / `EntityMentionRepository`
- [ ] `GraphExtractionService` — батч-извлечение по чанкам (5 чанков/вызов, максимум 40 чанков/документ)
- [ ] `extract_graph_task` — отдельная Celery-задача, запускается ПОСЛЕ того как документ стал "ready" (не блокирует загрузку)
- [ ] `chat_service.py`: `qdrant_search_executor` возвращает `{"results": ..., "graph_context": ...}` вместо голого списка чанков
- [ ] Обновить `tool_hints["docs"]` в системном промпте — упомянуть `graph_context`

**Отложено на потом (Phase 2b, не сегодня):** реальная страница `/knowledge-graph` на фронте (сейчас заглушка).

Принцип отображения:
- Force-directed граф (узлы-сущности + рёбра-связи, физика сама раскладывает связанные кластеры рядом) — библиотека `react-force-graph`
- Цвет узла — по `type` сущности (палитра + фоллбэк-цвет для незнакомых типов), размер узла — по количеству связей (хабы крупнее)
- Клик по узлу — панель деталей через существующий `Sheet`-компонент (тот же паттерн, что уже используется для источников в `MessageBubble.tsx`): описание + связанные сущности + превью чанков-упоминаний
- Фильтр по документу (иначе граф по всем документам сразу перегружен) + поиск/подсветка сущности по имени
- Нужны новые read-эндпоинты: `GET /api/v1/graph/entities`, `GET /api/v1/graph/relationships`

**Проверка:** загрузить документ с сущностями/связями, разнесёнными по разным чанкам, спросить вопрос требующий "хопа" по графу — сравнить с ответом без графа.
